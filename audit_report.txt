I limited the check to age because the pipeline's other numeric columns are identifiers or codes (subject_id, first_wardid), not real measurements and length of stay already has its own dedicated 99th-percentile cap earlier in the pipeline. To avoid leakage, the lower/upper bounds are computed from the training split only and reused unchanged on the test split so it's consistent with how every other preprocessing step in this pipeline already treats train vs. test. - To justify the 2.5 threshold, I compared outlier counts for age across the four levels from the lecture (0.5, 1.5, 2.5, 3.0). At 0.5 and 1.5, normal age values get wrongly flagged (19 and 5 respectively). At 2.5 and 3.0, no outliers are flagged at all, so the data doesn't distinguish between these two. I kept 2.5 since it's the lecture's recommended default and it is the smallest threshold that stops false-flagging ordinary age variation while staying conservative.

This only affected diagnosis, which had 82 different values in training, so now it's reduced to the top 15 plus "Other" instead of creating a bunch of almost-empty dummy columns.

## Done by Pablo
Identified some issues:
1. We split the data into a training set and a test set, which is correct. 
   We then preprocess the entire training set (e.g., imputation, scaling, one-hot encoding). 
   After that, we use GridSearchCV, which internally splits the training set into smaller training and validation folds to find the best hyperparameters. 
   Since the preprocessing was already fitted on the entire training set, each validation fold has already influenced the preprocessing (such as the scaling statistics and imputation values). 
   Ideally, the preprocessing should be fitted only on each inner training fold and then applied to its corresponding validation fold.

   We have 2 options to solve this:
      1. move all data-dependent preprocessing steps into an sklearn Pipeline (and ideally custom transformers), then pass that pipeline directly to GridSearchCV so each fold fits preprocessing only on its own training partition. This is more complex, hasn't been done in the lecture and imo overkill because its just to find the model parameters
      2. we add a validation split and use that to find our parameters. this is easier to implement and fits the level of this lecture better

## Done by Ons
-After reviewing the current implementation, I found that the outer
patient-grouped train/test split was correct, but the preprocessing was still
performed on the complete outer training set before the internal cross-validation.
This meant that the inner validation folds had already influenced preprocessing
steps such as missing-value handling, outlier limits, category selection,
one-hot encoding, scaling parameters and zero-variance feature removal.
The outer test set remained unseen, so the final test metrics were not directly
contaminated. However, the internal cross-validation scores could be optimistic,
and GridSearchCV could select different hyperparameters compared with a fully
leakage-free procedure.
I therefore adjusted the implementation so that preprocessing is now fitted
separately inside every grouped cross-validation fold. All preprocessing
parameters are learned only from the corresponding inner training fold and then
applied to its validation fold.
I also ensured that patient IDs are passed as groups during the inner
cross-validation, so records from the same patient cannot appear in both the
training and validation parts of a fold.
-After hyperparameter selection, preprocessing is fitted again on the complete
outer training set and applied once to the untouched outer test set. The final
models are then trained on the complete processed training set and evaluated on
the test set.
Lecture connection:
- L6 Data Leakage: preprocessing before proper data separation and failure to
  account for dependent samples can introduce leakage.
- L4 Splitting Data: cross-validation can be used when a separate validation
  set would be too small or unstable.
